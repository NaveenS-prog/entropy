# Phase 9 — Architectural Consistency & Architecture Debt Analyzer

## Overview

The **Architectural Consistency & Architecture Debt Analyzer** is Entropy's Phase 9 static analysis component designed to measure accumulated architectural debt, structural inconsistency, and organizational erosion across codebases.

### Core Architectural Principle

> **Entropy measures observable structural consistency and architectural debt patterns. It does NOT claim that code was written by AI, that an architectural pattern proves AI usage, that an architecture finding is a vulnerability, or that an architecture is objectively "good" or "bad". Entropy detects when a codebase establishes an observable structural convention, but comparable components fail to follow it consistently.**

---

## 1. What Architectural Consistency Means in Entropy

In healthy software systems, modules and components adopt consistent structural boundaries, clean dependency DAGs (Directed Acyclic Graphs), and standardized interaction conventions. Over time, as codebases grow through rapid contributions and feature additions, architectural decay occurs:
- Circular import dependencies form between modules.
- Intermediate domain or service boundaries are bypassed.
- Components obtain shared dependencies in conflicting ways.
- Direct environment lookups bypass centralized settings.
- Individual modules or classes accumulate excessive, divergent responsibilities (God Modules / God Classes).

Entropy analyzes these structural relationships entirely at the static AST and dependency-graph level, evaluating relative consistency across the repository.

---

## 2. What the Analyzer Detects and Does NOT Detect

### What It Detects:
- Statically observable circular import cycles between local modules.
- Bypassed intermediate layers (e.g. API route directly accessing database persistence while peer routes delegate to services).
- Divergent dependency acquisition patterns within the same component group.
- Ad-hoc environment lookups (`os.environ`, `os.getenv`) that bypass centralized settings.
- Highly concentrated multi-responsibility modules (God Modules) combining routing, database queries, security, and low-level system calls.
- Bloated classes with high method counts combining orthogonal domain operations (God Classes).
- Excessive cross-layer coupling spanning 4+ distinct system tiers.

### What It Does NOT Detect:
- It does **NOT** enforce a universal or dogmatic architectural paradigm (such as strictly enforcing Clean Architecture, Hexagonal, or MVC on projects that do not use them).
- It does **NOT** claim code was generated by an LLM or human developer.
- It does **NOT** classify architectural findings as security vulnerabilities or assert exploitability.
- It does **NOT** flag legitimate single-domain large files (such as an AST visitor with many visit methods or a math library) as God Modules.

---

## 3. Supported Language Scope & Limitations

- **Primary Supported Language**: Python (utilizing Entropy's AST parsing infrastructure).
- **Import Resolution**: Imports are resolved statically against repo-relative module paths and package hierarchies. Dynamic imports (`importlib.import_module(...)`), runtime `sys.path` manipulations, or dynamic evaluations are never executed.
- **Other Languages**: Non-Python files (e.g. TypeScript, JavaScript, Go) are marked appropriately as unsupported for this analyzer until corresponding AST models are implemented. No fabricated findings are emitted.

## 4. Detection Rules

| Rule ID | Rule Title | Severity | Confidence | Description |
| :--- | :--- | :--- | :--- | :--- |
| **ENT-ARCH-001** | Circular Module Dependency | Medium | High | Statically observable circular import dependencies between local modules. Canonical cycle ordering prevents duplicate reports. |
| **ENT-ARCH-002** | Architectural Layer Boundary Violation | Medium | Medium | Direct jump from presentation layer to database/repository, bypassing an established intermediate service layer used by peers. |
| **ENT-ARCH-003** | Inconsistent Dependency Pattern | Low | Medium | Conflicting dependency acquisition in the same component group (e.g. manual instantiation vs dependency injection). |
| **ENT-ARCH-004** | Inconsistent Configuration Access | Low | High | Direct `os.environ` / `os.getenv` lookups in domain logic when a centralized settings module exists. |
| **ENT-ARCH-005** | God Module / Excessively Responsible Module | High | Medium | Module concentrating 4 or more orthogonal architectural responsibilities with high LOC and fan-out. |
| **ENT-ARCH-006** | God Class / Excessively Responsible Class | Medium | Medium | Class defining 10+ methods combining multiple distinct architectural concerns. |
| **ENT-ARCH-007** | Excessive Cross-Layer Coupling | Medium | Medium | Module directly importing from 4 or more distinct architectural tiers simultaneously. |
| **ENT-ARCH-008** | Inconsistent Architectural Pattern | Low | Medium | Component diverging from the dominant structural pattern established by peer modules in its functional group. |

---

## 5. Exclusions & False Positive Prevention

Architecture scanning strictly respects repository boundary rules:
- Test suites (`tests/`, `test/`)
- Test fixtures (`fixtures/`)
- Database migrations (`migrations/`, `alembic/`)
- Third-party packages and virtualenvs (`vendor/`, `node_modules/`, `.venv/`, `venv/`)
- Build outputs and distribution bundles (`dist/`, `build/`)
- Operational maintenance scripts (`scripts/`, `setup.py`)

  - `architectural_consistency`: `0.10`
  - `code_duplication`: `0.05`

- **Clean Score Invariant**: Repositories with zero architectural findings receive an architectural score of `0.0`.
- **Monotonicity Guarantee**: Remediation strictly decreases or preserves the score.

---

## 7. Safety & Zero Code Execution Guarantee

Entropy treats all repository code as untrusted input:
- Target files are read as text and parsed via `ast.parse`.
- Target code is **never imported** or dynamically evaluated.
- No application objects, decorators, or scripts are executed.
- Verified by automated canary tests proving that malicious code in the target repository produces zero execution side-effects.

---

## 8. AI Explanation Integration

Phase 7 AI assistance operates uniformly over `Finding` models:
- AI may explain the architectural inconsistency, rationale, and recommended refactoring pattern.
- AI **cannot** create, delete, suppress, or modify findings, severities, or scores.
- Deterministic static analysis remains the single source of truth.
